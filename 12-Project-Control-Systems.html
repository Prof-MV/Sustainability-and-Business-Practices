12  Project Control Systems

12.1 Learning Objectives

By the end of this chapter you will be able to:

  1. Describe the monitoring-and-control loop and the performance measurement baseline.
  2. Read the three earned-value curves: planned value (PV), earned value (EV), and actual cost (AC).
  3. Compute schedule and cost variance and the SPI / CPI performance indices.
  4. Forecast with EAC, ETC, VAC, and TCPI, and interpret them.
  5. Run integrated change control so the baseline stays meaningful.
  6. Report status honestly and recognize the “watermelon” trap.
Before we begin: the project has spent 60 % of its money — is it 60 % done?

Almost certainly not. “Percent of budget spent” and “percent of work finished” are different numbers, and the gap between them is the whole subject of this chapter.

12.2 Introduction: from a plan to a control system

You have planned the RC-vehicle project — scope, WBS, schedule, budget. It is now week 8. The sponsor asks the only question that matters at this stage: are we on track, and if not, how far off, and what will it cost to finish?

Answering that needs a control system: a closed loop that measures progress, compares it to the baseline, analyzes the variance, and drives a corrective action — then measures again.

The reference for “compare” is the performance measurement baseline — the approved scope + schedule + cost locked in at the end of planning (Chapter 9’s S-curve is its cost dimension).

Note

Industry snapshot. Earned value management is contractually mandated on large U.S. defense programs (EIA-748). Automotive programs run a lighter version at the milestone level. A food-plant capital project tracks committed vs. spent vs. installed. The math below is the same at every scale.

12.3 The three curves

Earned value management tracks three cumulative quantities against time:

Term Also called Meaning
PV — Planned Value BCWS The budgeted cost of the work scheduled to be done by now
EV — Earned Value BCWP The budgeted cost of the work actually done by now
AC — Actual Cost ACWP What has actually been spent to do that work

BAC (Budget At Completion) is the total baseline budget — where the PV curve ends.

12.4 The six core metrics

\[ \begin{aligned} \text{Schedule Variance} \quad SV &= EV - PV \\ \text{Cost Variance} \quad CV &= EV - AC \\ \text{Schedule Performance Index} \quad SPI &= EV / PV \\ \text{Cost Performance Index} \quad CPI &= EV / AC \end{aligned} \]

Reading Schedule Cost
Ahead / under \(SV > 0\), \(SPI > 1\) \(CV > 0\), \(CPI > 1\)
On plan \(SV = 0\), \(SPI = 1\) \(CV = 0\), \(CPI = 1\)
Behind / over \(SV < 0\), \(SPI < 1\) \(CV < 0\), \(CPI < 1\)

12.4.1 Worked Example 1: the RC-vehicle project at week 8

Baseline budget BAC = $620 000. By week 8 the plan said 35 % of the work should be done; 30 % is actually done; $210 000 has been spent.

The project is behind schedule and over cost — and this is visible in week 8, while there is still time to act, instead of as a surprise at the end.

12.5 Forecasting

Forecast Formula Meaning
EAC (Estimate At Completion) \(BAC / CPI\) Total cost if current cost efficiency holds
EAC (schedule too) \(AC + \dfrac{BAC - EV}{CPI \times SPI}\) If both cost and schedule performance persist
EAC (one-off overrun) \(AC + (BAC - EV)\) If the overrun so far was a one-time event
ETC (Estimate To Complete) \(EAC - AC\) Money still needed from here
VAC (Variance At Completion) \(BAC - EAC\) Projected total over/under budget
TCPI (To-Complete Performance Index) \(\dfrac{BAC - EV}{BAC - AC}\) The cost efficiency the remaining work must hit to still land on BAC

12.5.1 Try it yourself: EAC scenarios

Which EAC formula should you actually report?

It depends on why you are over. If a one-time event caused it (a failed test you have since fixed), \(AC + (BAC - EV)\) is fair. If the overrun reflects how the team is fundamentally working (rates, productivity), \(BAC/CPI\) is the honest number. If you are also behind schedule and recovery will cost overtime, the \(CPI \times SPI\) version is the most conservative. Report the one your evidence supports — and say which assumption you made.

12.6 Reading the S-curve honestly

  • Spend is not progress. A project can be on budget (AC ≈ PV) and badly behind (EV ≪ PV) — it just has not done the work yet.
  • The “watermelon” report — green on the outside, red on the inside. High-level status shows green because spend matches plan, while the earned value underneath is red.
  • Leading vs. lagging indicators. SPI and CPI are somewhat lagging. Leading signals — rising defect find-rate, slipping sub-milestones, key staff leaving — warn you earlier. Watch both.

12.7 Integrated change control

Control only works against a meaningful baseline. Every change request goes through the same gate as in Chapter 3: assess the impact on scope, schedule, and cost; approve or reject; and if approved, re-baseline so future variance is measured against the new plan — not the old one you can no longer hit. Configuration management keeps the product definition (drawings, specs, software versions) in step with the approved baseline.

12.8 Status reporting

The course’s Project Manager Report and Team Member Report templates are the reporting instruments: they roll up progress, cost, schedule, risks, and issues on a fixed cadence. Good reporting is honest (report the red while it is still fixable), consistent (same metrics every period so trends are visible), and actionable (every variance has an owner and a next step). A dashboard that only ever shows green is not a control system — it is a comfort blanket.

12.9 Key Takeaways

  • Control is a closed loop: measure → compare to baseline → analyze variance → act, every reporting period.
  • Track PV (work scheduled), EV (work done), AC (money spent), all in budget dollars, against BAC.
  • \(SV = EV - PV\), \(CV = EV - AC\), \(SPI = EV/PV\), \(CPI = EV/AC\). Below 1 / negative = behind / over.
  • Forecast with EAC (\(BAC/CPI\) is the common honest form), ETC \(= EAC - AC\), VAC \(= BAC - EAC\), TCPI \(= (BAC-EV)/(BAC-AC)\).
  • Spend is not progress. Beware the watermelon report; watch leading indicators, not just SPI/CPI.
  • Keep the baseline meaningful through integrated change control and configuration management.
  • Report honestly, consistently, and actionably — every variance gets an owner.

12.10 Case Study: Meridian R/C — Week 12

Tip📁 CASE STUDY FILE — Week 12: One Good Number Doesn’t Make a Good Week

Day 50, and it’s time to run the loop this chapter just walked you through — measure, compare, analyze, act — against real Trailblazer numbers instead of a textbook example. Sofia Reyes’s weekly report lands with a summary line that looks encouraging at a glance: spend is roughly tracking the plan. You know better than to stop at a glance.

Metric Value
BAC (Budget At Completion) $761,300
PV (Planned Value, day 50) $560,000
EV (Earned Value, day 50) $520,000
AC (Actual Cost, day 50) $545,000

You run the four core numbers yourself before the steering call. CV = EV − AC = $520,000 − $545,000 = −$25,000 — over budget. SV = EV − PV = $520,000 − $560,000 = −$40,000 — behind schedule. CPI = EV/AC = 520/545 ≈ 0.95. SPI = EV/PV = 520/560 ≈ 0.93. Running BAC/CPI forward gives an EAC of roughly $798,000 — a forecast, not a certainty, but not a comfortable one either.

The schedule slip traces to one place: activity H, toy-safety certification, which has sat on the critical path with zero float since the CPM network was first built back in Week 6. The certification lab pushed back its review date, and because H has no float, every day it slips is a day the whole 67-day project finish slips with it.

The cost story is the sharper lesson. Two weeks ago, Marcus Webb talked MCS down from $145,000 to $136,000 for the motor-and-controller package — a genuine $9,000 win, hard-negotiated, real money, and the whole point of using the competing Paragon quote as leverage. So why is AC still running $25,000 ahead of EV? Because elsewhere on the project, packaging samples had to move by expedited freight to protect the schedule, and that bill quietly ate the MCS saving and then some. A favourable variance on one activity, read on its own, told the team nothing reliable about the project’s overall health — exactly the trap this chapter’s “watermelon” warning describes: green on the outside, red once you look underneath.

There is a sliver of good news buried in the bad. At roughly $798,000, the EAC still sits just under Daniel Cho’s $800,000 charter ceiling from Week 3 — a thin margin, but a margin, assuming nothing else slips before Week 13’s closeout.

12.11 Practice Problems

Problem 1: Full EVM snapshot

BAC = $400 000. At the status date: PV = $180 000, EV = $150 000, AC = $165 000. Compute SV, CV, SPI, CPI, EAC (BAC/CPI), ETC, VAC, TCPI, and state the project’s condition in one sentence.

Solution.

BAC <- 400000; PV <- 180000; EV <- 150000; AC <- 165000
SV <- EV - PV; CV <- EV - AC; SPI <- EV / PV; CPI <- EV / AC
EAC <- BAC / CPI; ETC <- EAC - AC; VAC <- BAC - EAC
TCPI <- (BAC - EV) / (BAC - AC)
cat(sprintf("SV=$%s  CV=$%s  SPI=%.3f  CPI=%.3f\n",
            format(SV, big.mark=" "), format(CV, big.mark=" "), SPI, CPI))
cat(sprintf("EAC=$%s  ETC=$%s  VAC=$%s  TCPI=%.3f\n",
            format(round(EAC), big.mark=" "), format(round(ETC), big.mark=" "),
            format(round(VAC), big.mark=" "), TCPI))
SV=$-30 000  CV=$-15 000  SPI=0.833  CPI=0.909
EAC=$440 000  ETC=$275 000  VAC=$-40 000  TCPI=1.064

Behind schedule (SPI 0.83) and over cost (CPI 0.91); projected to finish about $40 000 over budget, and the remaining work must run at TCPI ≈ 1.06 to still hit BAC.

Problem 2: On budget but in trouble

A project reports PV = $500 000, EV = $400 000, AC = $400 000. The sponsor sees “spend exactly matches earned value — CPI = 1.0 — we’re fine.” Are they?

Answer. Cost efficiency is fine (CPI = 1.0), but SPI = EV/PV = 0.80 — the project has completed only 80 % of the work it should have by now. It is 20 % behind schedule and will either finish late or need to spend more (overtime, added staff) to catch up, which will then push CPI below 1. This is the classic watermelon: the cost view is green, the schedule view is red.

Problem 3 (discussion): re-baseline or not?

At week 8 the RC-vehicle project is forecast (EAC) at $700 000 against a $620 000 BAC, mostly because the retailer added a second body colourway (an approved scope change) and the new line’s learning curve ran longer than planned. Should you re-baseline?

Discussion points. Split the two causes. The approved scope change is a legitimate reason to re-baseline — the extra colourway was authorised, so the budget and schedule should be formally updated and future variance measured against the new plan. The learning-curve overrun is performance against the plan, not a change to the plan — that stays as variance you must recover or explain. Re-baselining to bury performance problems (“we’ll just move the goalposts”) destroys the value of the control system; re-baselining for authorised changes keeps it honest.
